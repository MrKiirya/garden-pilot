Status: in-review

Hardware check: none. No firmware YAML changes. The Dockerfile changes shape (named uv stage), so the author

## Goal
Every pull request and every push to `master` runs the same checks a contributor runs locally, inside the same
devcontainer image: yamllint + `esphome config` (`script/lint`), the pytest repo checks (`script/test`), and a
real ESP32 firmware compile against two ESPHome versions: the one pinned in `uv.lock` and the lowest version
the project supports. That lowest version is found in this task and recorded in one place. A weekly canary
builds against the newest stable ESPHome on PyPI and opens (or updates) one GitHub issue when the build breaks.
It closes that issue when the build passes again. Dependabot proposes updates for the pinned actions, the
Python dev dependencies (incl. ESPHome) and the devcontainer images. All workflows are least-privilege, pinned
by commit SHA and need no secrets. The `master` ruleset is not configured here: the human applies it by hand
from the list in this file.

## Context

### Decisions (implement these; justify any deviation in Implementation notes)

**D1. One CI workflow, three required jobs with stable names.** `.github/workflows/ci.yml`, `name: CI`:
- Triggers:
  - `pull_request` with `branches: [master]`.
  - `push` with `branches: [master]`.
  - `workflow_dispatch`.
- No `paths` filters. Required checks must always report, or docs-only PRs would block.
- Jobs and their display names. These are the required status check names, so never rename them casually:
  - `checks`: runs `script/lint && script/test` in the devcontainer. One job instead of two, which saves one
    image build. `script/lint` already includes `yamllint --strict .`.
  - `compile`: a matrix over `target: [pinned, minimum]` with `fail-fast: false` and
    `name: compile (${{ matrix.target }})`. It produces the checks **`compile (pinned)`** and
    **`compile (minimum)`**. The matrix holds **labels, not version numbers**, so the check names survive
    ESPHome bumps. The version behind each label is resolved by `script/_esphome` (D3).
- `runs-on: ubuntu-24.04` (pinned image; `ubuntu-latest` moves under us).
- `timeout-minutes`: 20 for `checks`, 60 for `compile`.
- Concurrency:
  - `group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}`.
  - `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.
  - Superseded PR runs are cancelled. Runs on `master` pushes always finish.

**D2. Jobs run inside the devcontainer via `devcontainers/ci`.** Every build job does three things:
- `actions/checkout` with `persist-credentials: false`.
- Prepares the cache volumes (D4).
- Runs `devcontainers/ci` with:
  - `imageName: garden-pilot-devcontainer`: a local name with no registry. The action marks it required.
  - `push: never`.
  - Default `configFile`.
  - `runCmd`: the job's command.
  - `env:`: the `GP_*` variables, one `NAME=value` per line.

`postCreateCommand` (`script/setup` = `uv sync`) runs as part of `devcontainer up`, so the venv comes from
`uv.lock` exactly as it does locally. The canary `report` job (D6) is the only job that does not use the
devcontainer: it only calls `gh` and checks out nothing.
- Checked ([devcontainers/ci action.yml](https://raw.githubusercontent.com/devcontainers/ci/main/action.yml),
  [docs/github-action.md](https://github.com/devcontainers/ci/blob/main/docs/github-action.md), latest tag
  `v0.3.1900000450`, `main` runs on `node24`):
  - inputs: `imageName`, `imageTag`, `subFolder`, `configFile`, `runCmd`, `env`, `inheritEnv`, `push`
    (`never`/`filter`/`always`), `refFilterForPush`, `eventFilterForPush`, `skipContainerUserIdUpdate`
    (default `false`), `cacheFrom`, `cacheTo`, `noCache`, `platform`, `useNativeRunner`.
  - output: `runCmdOutput`.
  - post step: pushes only when the push filter matches, so `push: never` is set explicitly.
- `runArgs` on GitHub-hosted Ubuntu + Docker:
  - `--security-opt label=disable`: Docker accepts it and ignores it when there is no SELinux (Ubuntu uses
    AppArmor).
  - `--device=${localEnv:GP_SERIAL_DEVICE:/dev/null}`: resolves to `--device=/dev/null`, a real character
    device. Docker should accept it. This was verified only under Podman in task 002, so **the PR's first run is
    the proof**.
  - `--group-add=${localEnv:GP_SERIAL_GROUP:vscode}`: Docker resolves the group name inside the image, where
    `vscode` exists.
  - If Docker rejects any of them, **stop and report**. Do not change `devcontainer.json` semantics without the
    human: USB users depend on them. A possible fallback is a CI-only override, but it needs a decision.
- `updateRemoteUserUID` (on by default; the action does not skip it) remaps `vscode` to the runner's UID (1001).
  So the workspace bind mount and the cache dirs (D4) are writable, and git sees no "dubious ownership".

**D3. ESPHome version selection: `script/_esphome` + `GP_ESPHOME`, and no lock-file edits.**
- New POSIX-sh helper `script/_esphome`. `GP_ESPHOME` selects the version (default `pinned`):
  - `pinned` → `uv run --no-sync esphome "$@"`: the venv from `uv.lock`.
  - `minimum` → the version from `[tool.garden-pilot] esphome-minimum` in `pyproject.toml`, run as
    `uvx --isolated --from "esphome==<v>" esphome "$@"`.
  - `latest` → `uvx --isolated --refresh-package esphome --from esphome esphome "$@"`. uv skips pre-releases
    by default, so this is the newest stable release.
  - `<YYYY.M.P>` → that exact version via `uvx`. This form is used for bisecting.
  - Anything else exits 2 with a usage message. Validate with `^[0-9]{4}\.[0-9]+\.[0-9]+$`, which also
    prevents injection from the canary's dispatch input.
  - `script/_esphome --resolve` prints the resolved version (or `latest`) and runs nothing, so the unit tests
    can check the mapping without a toolchain. Read `pyproject.toml` with `sed`/`grep`, not Python.
- Why `uvx` and not `uv pip install esphome==X` into the venv:
  - It never touches the project venv or `uv.lock`.
  - It works the same on a host and in the container.
  - Its environments live in the uv cache (`~/.cache/uv`), which CI caches (D4).
  - `UV_PYTHON_DOWNLOADS=never` makes it use the image's Python 3.13.
  - Trade-off: the minimum and latest legs resolve ESPHome's transitive dependencies fresh, without a lock.
    That matches what a user installing that version gets.
- **Single source of truth for the minimum:**
  ```toml
  [tool.garden-pilot]
  # Lowest ESPHome release this configuration supports (SPEC §6). CI compiles it.
  esphome-minimum = "YYYY.M.P"
  ```
  This goes in `pyproject.toml`, next to the pin. uv ignores foreign `tool.*` tables, and Dependabot does not
  edit them.
  - The workflow never spells out a version.
  - Unit tests cross-check this value against SPEC §6. They also check the pin against `uv.lock` and SPEC §6.
- `script/config` (modify) calls `sh script/_esphome config …` instead of `uv run --no-sync esphome config …`,
  so `GP_ESPHOME` works for config validation too. Behaviour with `GP_ESPHOME` unset stays the same.
- `script/compile` (new, executable): `script/compile [CONFIG]`, default `garden-pilot.yaml`.
  - Prints `ESPHome <version>` first (`sh script/_esphome version`).
  - With a real `secrets.yaml` and `GP_SECRETS` != `example`, it compiles in place.
  - Otherwise it stages into the fixed, git-ignored dir `.esphome/example-build/`:
    - the config;
    - `packages`, `hardware` and `components` if they exist, the **same list as `script/config`**;
    - `secrets.example.yaml` copied as `secrets.yaml`.
    - Then it compiles there. The dir is fixed (not `mktemp`) so local reruns are incremental.
  - Before copying, it refreshes the staged sources (removes everything except the nested `.esphome/` build
    dir).
  - It prints a one-line note that a firmware built with example secrets must not be flashed.
- This satisfies "secrets.example.yaml copied to secrets.yaml inside the job". The copy lives under
  `.esphome/`, so CI and local reproduction never create `secrets.yaml` in the checkout. That would clobber a
  contributor's real file if they reproduce CI locally.
- Compile runCmd: `script/compile && uv cache prune --ci`, with `env` `GP_SECRETS=example` and
  `GP_ESPHOME=${{ matrix.target }}`. `uv cache prune --ci` keeps the saved cache small (uv's CI
  recommendation).

**D4. Toolchain caches: bind-backed named volumes + `actions/cache`.**
- `devcontainer.json` mounts the named volumes `garden-pilot-cache` → `~vscode/.cache` and
  `garden-pilot-platformio` → `~vscode/.platformio`. The CI config is not changed. Before `devcontainers/ci`,
  the job creates volumes **with the same names** that are backed by host dirs:
  ```sh
  docker volume create --driver local --opt type=none --opt o=bind \
    --opt device="$RUNNER_TEMP/gp-cache" garden-pilot-cache
  ```
  Do the same for `gp-platformio`, and `mkdir -p` both dirs first. `devcontainer up` then mounts the existing
  volumes, so the container writes straight into host dirs that `actions/cache` can save and restore.
  - CI uses the committed config, with no CI variant.
  - A `.devcontainer/ci/` variant was rejected: it would break `test_variants_differ_only_in_display_settings`
    and drift from the local environment.
  - Keep the snippet inline in each job (it is small); no composite action.
  - **Container paths stay constant** (`~vscode/.cache/...`), so absolute paths inside the ESP-IDF install stay
    valid after a restore.
- Cache entries (`actions/cache`, restore + save; save happens automatically on a key miss):
  - `checks`:
    - path: `${{ runner.temp }}/gp-cache/uv`
    - key: `gp-uv-v1-${{ runner.os }}-${{ hashFiles('uv.lock') }}`
  - `compile`:
    - paths: `${{ runner.temp }}/gp-cache/uv`, `${{ runner.temp }}/gp-cache/esphome` (ESP-IDF, native
      toolchain since ESPHome 2026.7) and `${{ runner.temp }}/gp-platformio` (ESPHome < 2026.7 and the `host`
      platform).
    - key:
      `gp-toolchain-v1-${{ runner.os }}-${{ matrix.target }}-${{ hashFiles('pyproject.toml', 'uv.lock') }}`.
      `pyproject.toml` holds both the pin and the minimum.
  - **No `restore-keys`**:
    - a version bump starts cold (one ~5 min run) instead of piling old ESP-IDF versions into the cache;
    - entry sizes stay bounded under the 10 GB per-repo limit (LRU eviction, 7 days unused).
- The ESPHome build dir (`.esphome/example-build/.esphome/`) is not cached. Follow-up if warm compiles are slow.
- Checked ([actions/cache](https://github.com/actions/cache), latest `v6.1.0`, Node 24):
  - inputs: `path`, `key`, `restore-keys`, `lookup-only`, `fail-on-cache-miss`.
  - output: `cache-hit`.
  - Caches are scoped to branch, and a PR can read caches from the default branch.
  - 10 GB per repo; caches unused for 7 days are evicted.

**D5. No registry cache for the devcontainer image (for now).** Each build job builds the image (base pull +
apt). Rejected for this task: pushing to GHCR from `master` and using `cacheFrom` on PRs. Reasons:
- It needs `packages: write` in a separate job.
- A GHCR package starts private, so the human must make it public by hand.
- PRs from forks can't push.
- Every Dependabot base-image bump invalidates it anyway.
- Buildx `type=gha` caching was also rejected: it needs the runtime token, eats into the same 10 GB budget and
  adds another action.

The image build time is recorded (Acceptance criteria). If it is above ~3 min per job, add the GHCR variant as a
follow-up.

**D6. Weekly canary workflow `.github/workflows/canary.yml`, `name: Canary`.**
- Triggers:
  - `schedule` with one weekly cron, e.g. `"23 5 * * 1"` (an off-the-hour minute on Monday).
  - `workflow_dispatch` with one optional input, `esphome` (string, default `latest`), so the issue path can be
    tested with a known-bad version.
  - No push/PR triggers.
- `concurrency: {group: canary, cancel-in-progress: false}`.
- Top-level `permissions: {}`.
- Job `canary`:
  - `permissions: {contents: read}`, `timeout-minutes: 60`.
  - Uses the same volume + `devcontainers/ci` setup as `compile`, with `GP_ESPHOME=${{ inputs.esphome ||
    'latest' }}` in the action's `env` input. Never interpolate it into a shell `run:`; `script/_esphome`
    validates it.
  - `runCmd` writes `sh script/_esphome version` to `.esphome/canary-version`, then runs `script/compile`.
  - A host step with `if: always()` reads that file and exposes the version as job output `version`. Then
    writes it to `$GITHUB_STEP_SUMMARY`.
  - Caches: restore only (`actions/cache/restore`), using the **pinned** compile key as the key. The canary must
    not save entries for versions nobody pins. Usually latest == pinned, so it starts warm.
- Job `report`:
  - `needs: canary`, `if: always() && needs.canary.result != 'cancelled'`.
  - `permissions: {issues: write}` and nothing else. `timeout-minutes: 5`.
  - No checkout. Uses the preinstalled `gh` with `GH_TOKEN: ${{ github.token }}` and
    `GH_REPO: ${{ github.repository }}`. Pass the run URL, the result and the version via `env:`.
  - Dedupe by the label `canary-failure`. Create it with `gh label create canary-failure --force …`.
  - Title: "Canary: firmware build fails with the latest ESPHome".
  - On failure:
    - if an open issue with the label exists, add a comment (version, run URL);
    - otherwise create the issue with the label, the version, the run URL and a pointer to CLAUDE.md
      "Bumping ESPHome".
  - On success: if an open labelled issue exists, comment "passes again with ESPHome <version>" and close it
    (`--reason completed`). Otherwise do nothing.
  - Closing on success is chosen: the issue tracks "currently broken", and history stays in the closed issue.
- Guard both jobs with `if: github.repository == 'MrKiirya/garden-pilot'` (combined with the `if` above), so
  forks that enable Actions don't run the canary.
- Nothing is committed. The canary never edits `pyproject.toml`/`uv.lock`.

**D7. Dependabot `.github/dependabot.yml` (version 2), weekly on Monday.**
- `github-actions`, `directory: "/"`:
  - One group `actions` (`patterns: ["*"]`).
  - `commit-message: {prefix: ci, include: scope}` → `ci(deps): …`.
  - Dependabot updates both the SHA pin and the `# vX.Y.Z` comment.
- `uv`, `directory: "/"`:
  - Updates `pyproject.toml` + `uv.lock` together. Supported since March 2025
    ([uv ↔ Dependabot](https://docs.astral.sh/uv/guides/integration/dependabot/), not fetchable from here;
    confirmed via search).
  - Group `python-dev-tools` with patterns `pytest`, `pyyaml`, `yamllint`. **`esphome` is not grouped**, so it
    gets its own PR.
  - `commit-message: {prefix: chore, include: scope}` → `chore(deps): …`, as CLAUDE.md requires.
  - `cooldown: {default-days: 7, semver-patch-days: 3}`. ESPHome's monthly `.0` releases often get quick
    patch releases. Cooldown is supported for uv. Dependabot also applies a default 3-day cooldown since
    July 2026.
- `docker`, `directory: "/.devcontainer"`:
  - Group `devcontainer-images` (`patterns: ["*"]`), prefix `chore`, scope included.
  - Dependabot updates tag **and** digest when both are pinned.
- **ESPHome bumps: let Dependabot open them, and gate them with a check.** The unit check
  `test_spec_pinned_version_matches_pyproject` fails while SPEC §6 still shows the old pin. So the Dependabot
  PR goes red until a human pushes a `docs:` commit onto that branch. The commit updates SPEC §6 and confirms
  the minimum.
  - Chosen over "ignore esphome and rely on the canary": the Dependabot PR compiles the new version in CI
    before merge (the real proof). The red check keeps the CLAUDE.md "Bumping ESPHome" step from being
    forgotten.
  - Side effect: once a human commits to a Dependabot branch, Dependabot stops rebasing that PR. That is fine
    for a one-off bump.
- **`COPY --from=<image>` is not seen by Dependabot.** dependabot-core issue
  [#5103](https://github.com/dependabot/dependabot-core/issues/5103) is open, and
  [PR #12988](https://github.com/dependabot/dependabot-core/pull/12988) is unmerged. So the Dockerfile moves uv
  to a named stage:
  ```dockerfile
  FROM ghcr.io/astral-sh/uv:<x.y.z>@sha256:<digest> AS uv
  FROM mcr.microsoft.com/devcontainers/python:3-3.13-trixie@sha256:<digest>
  COPY --from=uv /uv /uvx /bin/
  ```
  - The uv stage must come first: a stage must be defined before it is referenced.
  - Keep uv at the current version and add its digest.
  - The final stage is still the devcontainer image, so the CLI's metadata and UID handling are unchanged.
  - Update the header comment: replace "until Dependabot (task 003)" with "Dependabot
    (`.github/dependabot.yml`) proposes tag + digest bumps".
  - Note on the devcontainers/python tag `3-3.13-trixie`: if Dependabot ever proposes a tag that changes the
    Python minor, `test_base_image_matches_python_version` turns that PR red. The human closes it or adds an
    `ignore` rule. Do not add `ignore` rules up front.
- No `devcontainers` ecosystem: we use no features.

**D8. Workflow security baseline (all workflows).**
- Top-level `permissions: {}`, plus explicit per-job `permissions`:
  - `contents: read` for build jobs;
  - `issues: write` for `report` only.
  - Never `write-all` / `read-all`, `packages`, `id-token` or `pull-requests: write`.
- Every `uses:` is pinned to a full 40-hex commit SHA with a trailing `# vX.Y.Z` comment. Use the latest
  release on the implementation day. Checked today:
  - `actions/checkout` v7.0.1 (Node 24; persists the token by default, so set `persist-credentials: false`);
  - `actions/cache` v6.1.0;
  - `devcontainers/ci` v0.3.1900000450.

  Resolve each tag to its commit SHA (e.g. `git ls-remote --tags https://github.com/<owner>/<repo>`; for
  annotated tags use the peeled `^{}` commit).
- `pull_request` only, never `pull_request_target` or `workflow_run`. Workflows need no secrets: no
  `${{ secrets.* }}` anywhere. `github.token` appears only in `report`.
- No `${{ github.event.* }}`, `${{ github.head_ref }}` or `${{ inputs.* }}` inside `run:` scripts. Pass such
  values via `env:`.
- `timeout-minutes` on every job.
- yamllint: `.yamllint` sets `truthy: check-keys: false`, so a bare `on:` key passes `yamllint --strict`. Keep
  lines ≤ 120 chars and use 2-space indentation with consistent sequence indentation. PyYAML reads `on` as the
  boolean `True`, so the tests must look up both `"on"` and `True`.

**D9. Finding the minimum ESPHome version (implementer, before writing it down).**
1. List the stable releases ≥ 2026.2.3 from `https://pypi.org/pypi/esphome/json` (`releases` keys, skip
   `b`/`rc`, ascending). The latest stable today is 2026.9.1, which equals the pin.
2. For **each** version, run
   `GP_ESPHOME=<v> GP_SECRETS=example script/config`.
   Config validation rejects unknown options and component schemas. Record pass/fail per version as a table in
   Implementation notes. Do a linear scan, not a binary search: it is about 20 versions, and failures may not
   be monotonic.
3. The floor is the lowest version such that it **and every later stable release** pass. It is never below
   2026.2.3 (the sprinkler `millis()` fix, SPEC §3).
   - Options that may raise the floor: `mipi_spi` ILI9341 with `transform`, LVGL options, `xpt2046`, the
     `esp32-s3-devkitc1-n16r8` board id (before 2026.7 this goes through PlatformIO), and `wifi.min_auth_mode`
     (added in 2025.11, below the floor already).
4. Optionally compile the candidate locally (`GP_ESPHOME=<v> GP_SECRETS=example script/compile`). **CI
   `compile (minimum)` on the PR is the final proof.** If it fails, raise the floor to the next passing version
   and push again. Record every attempt.
5. Write the result to `pyproject.toml` `[tool.garden-pilot] esphome-minimum` and to SPEC §6. Then remove open
   question 3 from SPEC §10 and add it under §10.1 Decided. Also remove the now-empty "Repository" heading.
